## Context

WinLink 当前围绕“链接管理”构建：任务编辑区负责选择源与目标、执行前校验和批量执行；受管区负责刷新状态、重建、删除链接和移除记录。对于目录源，现有能力只能落到符号链接或 Junction 这样的链接对象上，而不能把源目录真实复制到多个目标目录，再由 WinLink 持续帮用户跟踪后续变化。

这次变更要引入的不是“另一种目录链接”，而是一种新的受管分发模式。它需要和现有工作台、注册表、状态检查、执行历史及启动/刷新交互协同，但又不能破坏现有链接管理语义。

## Goals / Non-Goals

**Goals:**

- 为目录源新增可受管的镜像模式，使首次执行能够真实复制目录到多个目标。
- 为镜像源保存同步基线，并在启动或刷新时检测源目录变化。
- 在同步前识别目标目录的本地改动，并对覆盖风险给出明确提示。
- 复用 WinLink 现有的受管记录、执行历史和批量结果反馈模式。
- 让镜像目标的删除语义与“实体目录副本”相匹配。

**Non-Goals:**

- 不支持文件源的镜像模式。
- 不引入后台实时 watcher 或常驻同步服务。
- 不提供文件级 diff 浏览器或可视化冲突合并界面。
- 不做“只同步部分子目录”或“按规则排除文件”的高级镜像策略。

## Decisions

### D1：镜像模式独立于现有链接策略建模
- **选择**：把目录镜像同步作为独立受管模式处理，而不是塞进现有 `LinkCreationStrategy`。
- **理由**：链接策略表达的是磁盘链接对象；镜像模式表达的是实体目录副本和可重复同步流程，两者生命周期不同。
- **已考虑 alternative**：把镜像当成新的“创建策略”。被拒绝，因为现有删除、重建、状态检查都基于“目标是否仍是原链接对象”展开，复用后会语义混乱。

### D2：镜像同步采用真镜像语义
- **选择**：同步时复制新增、覆盖变更，并删除目标目录中源目录已不存在的内容。
- **理由**：这最符合“镜像同步”的用户预期，也能保证多个目标目录最终一致。
- **已考虑 alternative**：只做增量复制、不删除目标多余内容。被拒绝，因为它更像“补丁复制”，长期会让各目标目录漂移。

### D3：以目录快照摘要作为变更检测基线
- **选择**：记录源目录的相对路径、文件大小和最后写入时间，作为每次成功同步后的基线。
- **理由**：相比单纯目录时间戳更稳，比全文哈希更容易在第一版落地。
- **已考虑 alternative**：
  - 只看目录时间戳：太容易漏判或误判。
  - 全量文件哈希：精度更高，但第一版扫描成本和实现复杂度偏高。

### D4：启动和刷新共用同一套镜像变更检查流程
- **选择**：在应用启动后的初次状态刷新，以及用户手动刷新受管项状态时，都运行同一套镜像源检查逻辑。
- **理由**：用户已经明确要求“打开应用或刷新时发现源更变，提示是否同步”，统一逻辑也能减少两套状态来源。
- **已考虑 alternative**：只在进入“已链接”页签时检查。被拒绝，因为无法覆盖“打开应用即提示”的需求。

### D5：目标本地改动不静默覆盖，统一在同步前确认
- **选择**：同步前比较目标目录当前快照与上次成功同步时记录的目标基线；若发现目标被本地改动，要求用户明确确认后再继续同步。
- **理由**：真镜像必然有覆盖风险，必须让用户在动作前知情。
- **已考虑 alternative**：
  - 发现本地改动就直接阻止同步：过于僵硬，不利于“强制以源为准”的使用场景。
  - 发现本地改动仍静默覆盖：风险过高。

### D6：镜像目标删除时删除实体目录，移除记录仍保留纯登记删除
- **选择**：为镜像目标沿用“删除实际目标”和“只移除记录”两种动作，但前者对镜像目标删除的是实体目录而不是链接对象。
- **理由**：镜像目标本身就是受管复制物，删除动作应与其磁盘形态一致；同时保留“只移除记录”供用户放弃受管但保留目录。
- **已考虑 alternative**：镜像目标只允许移除记录，不允许删除实体目录。被拒绝，因为不符合用户“断开就删除目标目录”的预期。

## Risks / Trade-offs

- [Risk] 大目录的快照扫描和镜像复制可能导致刷新或同步耗时明显增加。 → Mitigation: 第一版先保持串行实现，但把快照逻辑和同步逻辑封装为独立服务，后续可再优化。
- [Risk] 只用大小和最后写入时间判断变化，极端情况下可能误判“内容未变”或“内容已变”。 → Mitigation: 在设计上保留未来替换为更强快照算法的空间。
- [Risk] 启动时弹出同步提示可能打断用户当前操作。 → Mitigation: 只在检测到实际变化时提示，并尽量合并为单次批量确认。
- [Trade-off] 第一版不做文件级差异展示。 → 接受理由：先解决“受管镜像 + 同步提示 + 覆盖确认”主路径，避免 UI 和复杂度膨胀。
- [Trade-off] 第一版不做后台 watcher。 → 接受理由：启动和刷新已经覆盖多数使用场景，且更符合 WinLink 当前桌面工具模型。

## Migration Plan

本 change 不涉及外部部署变更，但涉及本地持久化模型扩展。

- 为新建的镜像记录引入独立的受管模式字段和同步基线字段。
- 现有链接记录在读取时默认保持原有模式，不需要用户迁移。
- 只有用户新建目录镜像任务后，才会写入新的镜像字段。
- 若回滚到不支持镜像模式的版本，旧版本最多无法理解新字段，但不会影响已有纯链接记录的语义；因此应避免用旧版本继续管理已创建的镜像记录。

## Open Questions

- 启动或刷新时，如果同时有多个镜像源待同步，提示是聚合成一条批量提示，还是逐条提示更合适。
- 第一版是否需要在受管详情中显式展示“最近一次同步时间”和“最近一次检测时间”两个不同时间点。
