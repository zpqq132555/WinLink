用户当前问题集中在目录镜像初始化与“已连接”页交互两块，目标不是新增一套独立能力，而是把已有目录镜像功能补成完整闭环，并修正两个明显影响观感的 UI 行为。

背景判断：
- 当前工具已经支持目录镜像。
- `opsx-init` 在初始化项目时会先做一次真实目录复制。
- WinLink 随后再处理同一路径时，会把“目标已存在”统一视为冲突或跳过。
- 实际上这时镜像结果已经存在，缺的只是登记和同步基线。

第一轮问题收敛：
- 用户说明：`opsx-init` 自动目录镜像后，WinLink 会提示目标已存在、显示冲突，但镜像其实已经完成。
- 用户期望：此时 WinLink 不要再尝试建立一个新的目标镜像，而是“只做记录”，确保后续源目录更新时还能继续同步。

代码与规格探索后的结论：
- 现有 `ExecuteAsync` 只区分“目标不存在可以创建”和“目标存在直接跳过”。
- 现有 `RefreshAsync` 只服务于“已经登记过的目录镜像记录”。
- 因此系统里缺少一个明确中间态：目标目录已经存在，而且内容就是镜像结果，但还没有被登记成受管镜像。

这里出现过三个可选方向：

方案 1：目标已存在且与源一致时，自动采纳并登记
- 优点：用户最省操作。
- 风险：可能会把本来就存在、只是恰好内容一致的目录误收编为受管目标。

方案 2：目标已存在且与源一致时，提示“是否仅登记受管记录”
- 优点：最贴近用户描述，语义清楚，也能避免误采纳。
- 风险：比自动采纳多一次确认。

方案 3：只对 `opsx-init` 产物做特殊处理
- 优点：改动面看起来最小。
- 风险：语义割裂，系统会同时存在“通用目录镜像逻辑”和“init 特例逻辑”，后续维护更容易混乱。

推荐与确认：
- 推荐方案 2。
- 用户明确选择方案 2。

在方案 2 基础上的行为定义：

目录镜像新建执行时：
- 目标不存在：正常首次镜像复制 + 建记录。
- 目标已存在且与源快照一致：提示“检测到已有镜像，是否仅登记受管记录”；确认后只写 registry、source baseline、target baseline，不再重拷贝。
- 目标已存在但与源不一致：仍然视为冲突，不采纳。

这里还讨论过是否只让这条能力服务 `opsx-init` 路径：
- 最终建议：做成所有目录镜像模式都支持的通用能力。
- 理由：这样 UI、校验、执行、历史、后续同步语义都一致，不需要引入特例。
- 用户认可这一边界。

随后补充了两个“已连接”页的体验问题，一并纳入同一轮变更：

问题 A：目标详情出现“双通道展开”
- 当前目标表存在两套详情展示机制：
  - 选中行时自动显示 `RowDetails`
  - “原因”列中还有一个“查看详情”展开框
- 结果就是用户只要选中某条目标，就会自动看到“目标目录与最近一次同步基线一致”等大块信息。
- 这会让“选中”和“展开详情”混在一起，用户的感知是不一致的。

对此的结论：
- 不应该选中哪条就自动显示大块详情。
- “查看详情”应该成为唯一的详情入口。
- `StatusReason / 最近策略 / 最近同步 / 最近检查` 应该收进同一个详情区，由用户主动展开或折叠。

问题 B：移除记录后选中态跳回第一条
- 当前在“移除记录”后会刷新列表，但没有保留当前受管源任务和当前目标项的上下文。
- 结果是界面直接回到第一条受管源任务。
- 这不符合用户操作预期。

对此的结论：
- 删除某个目标记录后，如果当前受管源任务还有剩余目标，应继续停留在当前受管源任务上。
- 当前目标应尽量切换到剩余的相邻项或第一项，但不应直接跳到整个列表的第一条。
- 只有当当前受管源任务因为没有任何目标而被整个删除时，才回退到默认第一条。

最终本轮变更范围收敛为 3 组内容：
1. 目录镜像采纳：已有镜像一致时，确认后只登记，不重拷贝。
2. 已连接页详情交互统一：去掉“选中即展开”，统一由“查看详情”控制。
3. 移除记录后的选中保持：优先保留当前受管源任务和合理的当前目标。

当前已达成的一致：
- 本轮是一个组合型体验修正，不是单点 bugfix。
- 适合建一个 `superpowers-bridge` change，一次把 proposal、design、specs、tasks、plan 串起来。
