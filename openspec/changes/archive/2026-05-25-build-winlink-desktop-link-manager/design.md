## Context

WinLink 当前还没有应用代码，本次 change 的目标是把已经确认过的产品设计，正式转化成可执行的 OpenSpec 文档集合。产品定位已经明确：它不是命令行包装器，也不是浏览器壳，而是一个更偏原生 Windows 工具气质的桌面应用。

当前已确认的约束如下：
- 第一版优先采用 WPF 这类原生 Windows 技术路线。
- 主交互是单主窗口，搭配少量必要弹窗。
- `新建链接`、`已链接`、`预设` 是首版必须存在的三个主工作区。
- 工具只管理自己创建或记录过的链接映射，不做系统全盘实时扫描。
- 删除链接必须是严格保护模式，只允许删除仍与记录匹配的链接对象。
- 预设第一版只做固定模板，但底层结构不能堵死未来扩展。

## Goals / Non-Goals

**Goals:**
- 提供一个原生 Windows 桌面主窗口和统一的标签页导航结构。
- 以“一个源、多个目标”为核心模型，支持会话级任务编辑和批量执行。
- 为链接创建提供自动推荐、手动高级选项、执行前统一降级确认与尽力执行语义。
- 通过 AppData 下的 JSON 持久化记录受管链接，并在 `已链接` 页提供状态刷新、重建、严格删除和移除记录能力。
- 提供 AGENTS/skills 两组固定预设，并支持预览后直接应用或转成普通任务继续编辑。
- 为每次执行提供结果摘要和轻量历史回看能力。

**Non-Goals:**
- 不实现系统全盘实时扫描已有链接。
- 不实现用户自定义预设编辑器。
- 不实现跨会话的待执行任务草稿恢复。
- 不实现复杂筛选、搜索或危险的批量强制删除能力。
- 不在本次 change 中承诺最终具体 UI 视觉细节，只约束信息结构和行为边界。

## Decisions

### 1. 使用原生 Windows 桌面外壳，而不是 Web 壳
WinLink 第一版应采用原生 Windows 桌面路线，优先考虑 WPF。这更符合产品“现代一点，但别花”的目标，也更适合文件选择、菜单栏、列表分栏和系统路径交互。

备选方案：
- Electron/Tauri：界面自由度更高，但原生工具感更弱，并会增加壳层复杂度。
- WinForms：启动门槛低，但更容易做成老式工具，不符合目标气质。

### 2. 使用单主窗口 + 三个主标签页
主窗口统一承载 `新建链接`、`已链接`、`预设`，其余像执行历史、关于、降级确认等能力使用辅助弹窗承接。这能让首版结构足够清晰，同时保留后续菜单栏扩展空间。

备选方案：
- 向导式页面：不适合多任务暂存和重复管理场景。
- 多窗口管理器：信息切换成本高，不利于首版收敛。

### 3. 使用 AppData 下的 JSON 作为首版持久化方案
受管链接记录应放在 `AppData\Local\WinLink` 下，以 JSON 作为首版存储格式。模型以“源任务”为主，下面挂多个目标项，并保存最近检查结果、链接策略、展开状态等必要元数据。

备选方案：
- SQLite：查询更强，但第一版过重。
- EXE 同目录：在受保护目录里不稳，也不符合 Windows 应用习惯。

### 4. `新建链接` 采用左任务列表、右编辑区、底部执行区
`新建链接` 页使用统一工作台结构：左侧展示待执行任务列表，右侧编辑当前任务，底部提供 `先校验全部` 和 `批量执行`。这种结构比单大表单更匹配“当前会话暂存多条任务”的产品模型。

备选方案：
- 单页直排表单：初看更简单，但随着任务增多会变得拥挤。
- 完全混合的多类型任务表：会让文件/文件夹校验和策略边界变得模糊。

### 5. 每条任务锁定单一源类型
用户不用先选择全局“文件模式”或“文件夹模式”，但每条任务在选中源之后必须自动锁定为文件任务或文件夹任务，后续只允许添加同类型目标。这样既保留统一界面，又能保持底层策略清晰。

### 6. 使用两阶段校验
编辑期只做轻量即时检查，用于尽早暴露格式错误、冲突和必填项缺失。执行前再做完整校验，用于评估源是否存在、父目录是否可创建、权限是否足够、推荐链接方式是否可用以及是否需要降级。

### 7. 使用显式降级确认而不是静默回退
WinLink 必须先给出推荐链接策略。如果目标环境不支持该策略，但存在可接受替代项，则所有需要降级的目标必须在执行前统一汇总确认，不能后台偷偷改成其他语义。

### 8. 采用尽力执行，而不是原子批处理
一次批量执行中，任务和目标项应独立处理。遇到冲突项默认跳过，其他目标继续执行。这个选择与“多目标分发”“冲突默认跳过”“后续可重建”的产品模型一致。

### 9. `已链接` 页以受管注册表为唯一数据源
`已链接` 页不扫描系统全部链接，只展示本工具记录过的映射。进入页面时自动检查一次，也可手动刷新，并用顶部摘要、左侧源列表、右侧详情展示受管链接健康度。

### 10. 删除链接必须采用严格保护模式
`删除链接` 只在当前目标对象仍与记录匹配时才允许执行。任何已删除、被替换、被改指向或状态无法安全确认的目标，都必须阻止删除，并引导用户使用 `移除记录` 或手工处理。

### 11. 预设使用变量路径保存，预览时显示真实路径
预设内部应保存如 `%USERPROFILE%` 之类的变量路径，以便跨用户环境复用；UI 预览时必须展示展开后的真实路径，让用户在应用前看清本次会影响哪些位置。

### 12. 执行历史保留为轻量辅助能力
执行完成后先展示摘要，同时保留最近执行历史，入口放在独立弹窗而不是主标签页中，避免主窗口被日志视图污染。

## Risks / Trade-offs

- [Windows 链接能力受对象类型与环境权限影响较大] → 把“推荐策略”“实际执行方式”“降级确认”拆开建模，并在执行前统一校验。
- [严格删除会让部分用户觉得过于保守] → 明确展示阻止原因，并保留 `移除记录` 作为非破坏性的后备动作。
- [JSON 模型后期可能膨胀] → 首版先保持记录和历史职责清晰，必要时分成多个文档，而不是把所有状态揉进单文件里。
- [首版页面较多，交互容易发散] → 统一采用左列表右详情的骨架，并推迟筛选、搜索、用户自定义预设等非核心能力。
- [预设目标目录不一定存在] → 预览阶段显式提示，执行时自动补建父目录，并将该行为纳入验证结果说明。

## Migration Plan

- 在 `E:\project\nodejsProject\winlink` 下建立 WinLink 首版项目结构。
- 先落主窗口壳层、数据模型和链接操作抽象，再逐步接上三个主标签页。
- 在首版初始化时一并内置两组固定预设。
- 因为当前没有旧版本产品，本次 change 不需要历史数据迁移或回滚兼容策略。

## Open Questions

- 执行历史是否应与主记录拆成独立 `history.json`，还是先和主记录分文件但共享同一目录。
- UI 展开状态是否与主记录放在同一 JSON 中，还是单独维护一个轻量 UI 状态文件。
- 链接推荐与降级矩阵是否在第一版就做成独立策略表，还是先用小型规则服务承接。
